Multiple GPUs

One process per GPU, and the same engine

Engine coreexecute_model()MultiProcExecutor
rpc_broadcast_mqshared memory: every worker reads each message
worker_response_mqone queue per worker: results come back

The executor starts one daemon process per GPU. Each builds its own worker and loads its slice.

Broadcast: the engine puts the work on one shared queue, without blocking.

Run: each worker wakes up and runs its part of the forward pass. Workers exchange data between GPUs.

Collect: the engine waits on the output worker's queue only, and gets the result.

Source: A. Gordić, Inside vLLM (2025). TP = 8 shown.

Say tensor parallelism across 8 GPUs. Each GPU gets its own process. The class MultiProcExecutor starts them, and each goes through the same init device and load model steps we saw before. At start-up they hand back their response queue handles, and then each sits in a loop, blocked waiting for work.

The engine calls execute_model, as always. The executor puts the work on one broadcast queue in shared memory. It is implemented with shared memory, so all the workers on the node can read the same message.

All 8 wake up and run their slice, exchanging tensors between themselves.

The engine waits on the queue of the one worker that holds the final output. And here is the point: the scheduler, the blocks and the loop did not change at all. Only the object behind execute_model changed. That is an interface doing its job, and it is why we said the client and executor design was a lesson in itself.
