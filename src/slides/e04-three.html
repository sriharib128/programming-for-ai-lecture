Source: A. Gordić, Inside vLLM (2025)

Here is how vLLM uses those three tools. Start on the left: the API server. Each client request is a task on one asyncio event loop, because a request spends almost all of its time waiting for tokens. Remember: asyncio is concurrent, not parallel. One thread can hold hundreds of open requests.

In the middle, the engine core process. The main thread runs the loop you already know. If it had to read and write network sockets it could stall, and a stalled loop is an idle GPU. So there are two more threads. The input thread blocks on the socket, and when something arrives it puts it on a queue. The output thread does the reverse. These threads spend their lives waiting, which is exactly what threads are good at in Python. Two plain queues join them to the main thread.

On the right, one process per GPU. Heavy computation, full parallelism, and one owner per GPU. So: event loop for many waits, threads for waiting, processes for computing. These are the choices you would make from the rule of thumb on the last slide. Keep this picture in mind; in Part 6 you get to make these choices yourself.
