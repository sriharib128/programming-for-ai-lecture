A request stops when
  • it reaches its length limit
  • it samples the end token
  • it samples a token in stop_token_ids
  • the output contains a stop string
Source: A. Gordić, Inside vLLM (2025)

Now generate. It tokenizes each prompt, gives it an ID and an arrival time, and puts it in the waiting queue. Then the whole engine is this: while anything is unfinished, call step. Every call does three things. This is the same loop you wrote earlier, but for many requests at once.

First, schedule: decide which requests take part in this pass, and make sure they have memory. This is the next two slides.

Second, run the model and sample one token per request. In your loop this was the only line that mattered.

Third, postprocess: append the tokens, turn them into text, and check whether each request is finished. A finished request gives back its blocks immediately, which is what makes room for the next one.

These are the four ways a request can stop. Because the schedule is decided at every pass, a new request can join on the next one. Continuous batching is not a separate component; it follows from this loop.
