Each pass has a limit on how many tokens it can process.

Decode comes first. Running requests A, B and C each take one token.

Then prefill. D gets its blocks and moves to the running queue.

The budget runs out. E takes what is left, and the rest of its prompt waits for the next pass. F waits.

Waiting requests are taken in arrival order, or by priority. The V1 engine can mix prefill and decode in the same pass. Numbers here are illustrative.
Source: A. Gordić, Inside vLLM (2025)

Each pass has a budget: the maximum number of tokens it may process. Three requests are running, and three are waiting. How would you spend the budget?

vLLM serves decode first. Requests already running each take one token. A user already reading an answer should not see it stall because someone else arrived.

Then it turns to the waiting queue. D has 40 tokens in its prompt. It gets its blocks, and moves to running.

Now E. There are 21 tokens left in the budget and E needs 30. It takes 21 and finishes its prompt on a later pass. F keeps waiting. The older V0 engine could only run prefill or decode in one pass; the V1 engine mixes them. The next slide looks at how a request gets its blocks.
