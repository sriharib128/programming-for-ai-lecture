Waiting request: it stays in the waiting queue. Running request: the engine can preempt a lower-priority one, free its blocks, and recompute it later.

Source: A. Gordić, Inside vLLM (2025)

Here is the function at the centre of the memory design, allocate_slots. Request A has 17 new tokens.

Blocks hold 16 tokens each, so it needs the ceiling of 17 over 16: 2 blocks. One slot-level detail: the last block is only partly full, and that is the only waste there is.

It takes the first two blocks from the free queue and records them in req_to_blocks, a dictionary from request ID to its list of blocks. The queue is a doubly linked list, so both operations are constant time. When a request finishes, its blocks go back on the queue.

Now time passes and the queue is nearly empty. Request B needs three blocks, and two are free. Ask the room: what should happen? There is more than one reasonable answer.

It depends on the request. A request that has not started just stays in the waiting queue. A running request that needs one more block is a harder case: the engine can preempt a lower-priority request, free its blocks, and later compute it again from scratch. That is called recompute preemption. The older V0 engine could also swap a cache out; the V1 engine recomputes. Think about what that costs: the prefill has to be repeated.
