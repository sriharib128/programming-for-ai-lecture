Each hash includes the previous one, so equal hashes mean an equal start, not just one equal block.

Request 1: no hashes found. It computes all three blocks and records them.

Request 2: all three hashes found. It reuses those blocks and computes only its own last tokens.

Only complete blocks are cached. It speeds up prefill, not decode. On by default.

Source: A. Gordić, Inside vLLM (2025). Block numbers are illustrative.

Problem: many prompts begin the same way. Think of a system prompt, or the same instructions sent with every page. Without a cache, every request recomputes that prefix. Here two requests share three blocks of tokens.

How do we know two prefixes match? vLLM hashes each complete block. The trick is that each hash also includes the previous block's hash. So a match on h2 tells you h0 and h1 matched as well: the whole prefix is equal. If you have seen git or a blockchain, it is the same chain. Metadata such as a LoRA ID or a cache salt also goes in, so requests that should not share do not.

The first request finds no hashes, so it computes the three blocks and records which block holds each hash.

The second request finds all three, reuses those blocks, and only computes what follows. Here is a nice detail: when a request finishes, its blocks go back to the free queue, but the hash entries remain. A block is only truly forgotten when the free queue hands it to someone else. So the free list is also a least-recently-used cache, at no extra cost. Keep this in mind for the second half, where every request in a step shares the same instructions.
