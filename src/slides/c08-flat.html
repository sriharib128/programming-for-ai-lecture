slot_mapping says where in GPU memory each token's keys and values go. For B at position 9: block index 9 // 4 = 2, which is block 9, offset 1, so slot 9 × 4 + 1 = 37.

Source: A. Gordić, Inside vLLM (2025). Block size 4 for drawing; the default is 16.

One more piece, and this one is about tensors. A is prefilling five tokens. B and C are decoding, so they each contribute a single token. In ordinary PyTorch you would make a rectangle, and pad. Here more than half the cells are padding, and in a real batch, with long prompts, far more.

vLLM does not make a rectangle. It concatenates everything into one long sequence: seven tokens, no padding. A positions array records where each token sits in its own request, which is why B's token says 9. Attention masks ensure each token attends only to its own request's tokens. This is why requests can join and leave at every pass: nothing about the shape of the tensor depends on who is in the batch. Custom attention kernels make this efficient.

The last piece connects to paging. Every token has to write its keys and values somewhere, and slot_mapping is the address. Take B: position 9, blocks of size 4, so it is in the third block, block number 9, offset 1, which is slot 37. This is exactly virtual-to-physical address translation, computed for every token in the batch. That is the core of vLLM. Next, what it builds on top of this.
